## 3. DSA — The 15 Patterns (with worked examples) 🧩

**Stop solving random problems.** ~90% of interview questions are one of these patterns in disguise. Learn to **recognize the pattern from the problem statement**, then the solution follows.

### The pattern cheat-sheet (recognition triggers)

| Pattern | Trigger words / signals | Go-to complexity |
|---|---|---|
| Two Pointers | sorted array, pair/triplet, "in-place", palindrome | O(n) |
| Sliding Window | "contiguous subarray/substring", "longest/shortest ... with condition" | O(n) |
| Fast & Slow Pointers | linked-list cycle, middle of list | O(n) |
| Hashing / Set | "seen before?", counts, dedupe, complement lookup | O(n) |
| Binary Search | sorted, or "minimize the maximum / search on answer" | O(log n) |
| Stack | "matching/nested", "next greater element", parsing | O(n) |
| Trees BFS/DFS | levels → BFS; paths/subtrees → DFS | O(n) |
| Graphs BFS/DFS | grid/network, connectivity, shortest unweighted path | O(V+E) |
| Topological Sort | "ordering with prerequisites", dependency, DAG | O(V+E) |
| Union-Find | "connected components", "are these joined?" | ~O(α(n)) |
| Heap / Top-K | "K largest/smallest/most frequent", streaming | O(n log k) |
| Greedy | "maximum/minimum" with a local optimal choice, intervals | O(n log n) |
| Backtracking | "all combinations/permutations/subsets", constraints | exponential |
| Dynamic Programming | "number of ways", "min/max cost", overlapping subproblems | O(n·m) |
| Trie | prefix search, autocomplete, word dictionaries | O(word length) |

### Worked example A — Sliding Window (elaborate)

**Q: Longest Substring Without Repeating Characters.** Given a string `s`, return the length of the longest substring with all unique characters.

**Think out loud:** "It says *contiguous substring* with a *condition* (all unique) and asks for the *longest* — that's the sliding-window signal. I'll expand a window to the right, and when the condition breaks (a repeat), shrink from the left until it's valid again. I'll track the best length seen."

```python
def length_of_longest_substring(s: str) -> int:
    seen = {}          # char -> most recent index
    left = 0           # left edge of the window
    best = 0
    for right, ch in enumerate(s):
        # If we've seen ch inside the current window, jump left past it.
        if ch in seen and seen[ch] >= left:
            left = seen[ch] + 1
        seen[ch] = right
        best = max(best, right - left + 1)
    return best
```

**Complexity:** O(n) time (each character enters/leaves the window once), O(min(n, alphabet)) space.
**Edge cases to mention:** empty string → 0; all-same characters → 1; all-unique → n.
**Follow-up they may ask:** "Return the substring itself" (track `best_left`), or "at most K distinct characters" (same skeleton, condition becomes `len(window_counts) > K`).

### Worked example B — Dynamic Programming (elaborate)

**Q: Coin Change.** Given coins and an amount, return the fewest coins to make that amount, or -1.

**Think out loud:** "'Fewest ... to make amount' + reusable coins + overlapping subproblems ⇒ DP. Define `dp[a]` = fewest coins to make amount `a`. Base: `dp[0]=0`. Transition: for each coin `c`, `dp[a] = min(dp[a], dp[a-c] + 1)`. Answer is `dp[amount]`."

```python
def coin_change(coins: list[int], amount: int) -> int:
    INF = amount + 1
    dp = [0] + [INF] * amount            # dp[0]=0, rest "infinity"
    for a in range(1, amount + 1):
        for c in coins:
            if c <= a:
                dp[a] = min(dp[a], dp[a - c] + 1)
    return dp[amount] if dp[amount] != INF else -1
```

**Complexity:** O(amount × #coins) time, O(amount) space.
**Why bottom-up:** avoids recursion depth limits and is easy to reason about.
**The DP muscle to build:** always say the four things out loud — **state, transition, base case, answer.** If you can state those, you've solved it.

### Worked example C — Graphs / BFS (elaborate)

**Q: Number of Islands.** Count connected groups of `'1'` in a grid.

**Think out loud:** "Grid + connectivity ⇒ graph traversal. Each unvisited land cell starts a new island; I flood-fill (BFS/DFS) all connected land, marking visited, and increment the count."

```python
def num_islands(grid: list[list[str]]) -> int:
    if not grid: return 0
    rows, cols = len(grid), len(grid[0])
    count = 0
    def sink(r, c):
        if r < 0 or c < 0 or r >= rows or c >= cols or grid[r][c] != '1':
            return
        grid[r][c] = '0'                 # mark visited
        sink(r+1, c); sink(r-1, c); sink(r, c+1); sink(r, c-1)
    for r in range(rows):
        for c in range(cols):
            if grid[r][c] == '1':
                count += 1
                sink(r, c)
    return count
```

**Complexity:** O(rows × cols). **Trade-off to mention:** DFS recursion can stack-overflow on huge grids → use an explicit stack or BFS queue.

**➡️ For every other pattern:** pick 8–12 canonical LeetCode problems, solve out loud, and after each write a one-line "recognition note" ("saw *contiguous + longest* → sliding window"). That recognition note is what you're really training.

## 4. AI / ML Depth — Your Differentiator 🤖

For an AI SDE, this is where you turn "hire" into "strong hire" and land the ML team. **Understand, don't memorize** — they'll ask "why?" three times.

### 4.1 Core ML Q&A (elaborate answers)

**Q1. Explain the bias-variance trade-off.**
*Bias* is error from wrong assumptions — an over-simple model that underfits (e.g., linear model on a curvy relationship): high train **and** test error. *Variance* is sensitivity to the training data — an over-complex model that overfits (memorizes noise): low train error, high test error. Total error ≈ bias² + variance + irreducible noise. As model complexity rises, bias falls and variance rises; the goal is the **sweet spot** that minimizes test error. **How I'd manage it:** more data and regularization reduce variance; a richer model or better features reduce bias. *Signal to give:* mention that ensembles like Random Forests reduce variance (bagging) while boosting reduces bias.

**Q2. What is overfitting and how do you prevent it?**
Overfitting = the model learns the training data's noise, so it generalizes poorly (big gap between train and validation performance). **Prevention toolkit:** (1) more/augmented data; (2) regularization (L1/L2, dropout); (3) simpler model / fewer parameters; (4) early stopping on a validation set; (5) cross-validation to detect it; (6) for trees, pruning / max-depth. Always diagnose with a **train-vs-validation curve.**

**Q3. L1 vs L2 regularization?**
Both add a penalty on weights to the loss to discourage complexity. **L2 (Ridge)** penalizes the *square* of weights → shrinks them smoothly toward (but not to) zero; handles correlated features well. **L1 (Lasso)** penalizes the *absolute value* → drives some weights *exactly* to zero, giving **feature selection / sparsity**. Rule of thumb: L1 when you suspect many irrelevant features; L2 as the default smoother. Elastic Net = both.

**Q4. How does gradient descent work? Batch vs SGD vs mini-batch?**
GD minimizes a loss by iteratively stepping the parameters in the direction of the **negative gradient**: `w ← w − η·∇L(w)`, where η is the learning rate. **Batch** uses the whole dataset per step (stable, slow, memory-heavy). **Stochastic (SGD)** uses one example per step (noisy, fast, can escape shallow minima). **Mini-batch** (e.g., 32–256) is the practical middle ground and the industry default. Too-large η → divergence; too-small → crawling/stuck. Improvements: **momentum, RMSProp, Adam** (adaptive per-parameter learning rates).

**Q5. Precision vs Recall — and when do you care about each?**
Precision = TP / (TP + FP) — "of the ones I flagged positive, how many were right?" Recall = TP / (TP + FN) — "of all actual positives, how many did I catch?" **Choose by cost of error:** spam filter → favor **precision** (don't trash real email); cancer screening / fraud → favor **recall** (don't miss a real case). **F1** = harmonic mean balances both; use **PR-AUC** for imbalanced data and **ROC-AUC** for ranking quality. Always mention the **confusion matrix** as the source of truth.

**Q6. Your model has 95% accuracy but is useless. What happened?**
Almost certainly **class imbalance** — if 95% of samples are the negative class, a model that always predicts "negative" scores 95% while catching zero positives. **Fix:** stop using accuracy → use precision/recall/F1/PR-AUC; resample (oversample minority / SMOTE, or undersample majority); class weights in the loss; and pick a threshold from the PR curve, not the default 0.5.

**Q7. Generative vs Discriminative models?**
Discriminative models learn the decision boundary `P(y|x)` directly (logistic regression, SVM, most neural nets) — usually better raw accuracy. Generative models learn `P(x|y)` and `P(y)` and use Bayes to classify (Naive Bayes, GMM, and modern generative models like GANs/diffusion/LLMs which model the data distribution to *generate* new samples).

**Q8. Bagging vs Boosting?**
Both are ensembles. **Bagging** (e.g., Random Forest) trains many models *in parallel* on bootstrapped samples and averages → **reduces variance.** **Boosting** (AdaBoost, Gradient Boosting, XGBoost) trains models *sequentially*, each fixing the previous one's errors → **reduces bias**, often top accuracy on tabular data but more prone to overfitting and slower to train.

**Q9. How do you handle missing data?**
Understand *why* it's missing first (random vs systematic). Options: drop rows/columns (if few and random); **impute** (mean/median/mode, or model-based like KNN/regression imputation); add a "was-missing" indicator feature; or use algorithms that handle NaNs natively (e.g., XGBoost). Never impute using the test set (leakage).

**Q10. What is cross-validation and why use it?**
Instead of one train/test split, **k-fold CV** splits data into k parts, trains on k−1 and validates on the held-out fold, rotating k times and averaging. It gives a **more reliable, lower-variance estimate** of generalization and uses data efficiently — essential for hyperparameter tuning and small datasets. Use **stratified** k-fold for imbalanced classes.

### 4.2 Deep Learning & NLP Q&A (elaborate)

**Q11. Why activation functions? Compare ReLU/sigmoid/tanh.**
Without a non-linear activation, stacked layers collapse into a single linear transform — the network can't learn non-linear patterns. **Sigmoid** (0–1) saturates and causes **vanishing gradients**; **tanh** (−1–1) is zero-centered but still saturates; **ReLU** (`max(0,x)`) is the default — cheap, non-saturating for positives, enabling deep nets — but can "die" (stuck at 0), which **Leaky ReLU / GELU** address. Transformers typically use GELU.

**Q12. Vanishing/exploding gradients — cause and fixes.**
In deep nets, gradients are products of many terms (chain rule); if terms are <1 they shrink to ~0 (**vanishing** → early layers stop learning), if >1 they blow up (**exploding**). **Fixes:** ReLU-family activations, careful weight init (Xavier/He), **batch/layer normalization**, **residual/skip connections** (ResNet), gradient clipping (for exploding), and gated units (LSTM/GRU) for sequences.

**Q13. CNN vs RNN — when to use which?**
**CNNs** exploit spatial locality via shared convolutional filters → images, and any grid/local-pattern data; parameter-efficient and parallelizable. **RNNs/LSTMs/GRUs** process sequences with a hidden state carrying memory → time series, older NLP. RNNs struggle with long dependencies and are sequential (slow); **LSTMs** add gates to remember/forget long-range info. Today, **Transformers have largely replaced RNNs** for sequence tasks.

**Q14. Explain the Transformer and self-attention (the big one).**
The Transformer processes a whole sequence **in parallel** and models relationships between all tokens via **self-attention**. Each token is projected into **Query, Key, Value** vectors. Attention weight between tokens = softmax of (Q·Kᵀ / √d_k), then output = weighted sum of Values — i.e., each token "attends to" the tokens most relevant to it, regardless of distance. **Multi-head attention** does this in several subspaces in parallel (syntax, semantics, etc.). Since there's no recurrence, **positional encodings** inject order. Stacks of (attention + feed-forward + residual + layer-norm) blocks form the model. This is the foundation of BERT (encoder), GPT (decoder), etc. **Why it won:** parallelizable (fast on GPUs) + captures long-range dependencies far better than RNNs.

**Q15. What is an embedding?**
A dense, low-dimensional vector representation of a discrete item (word, user, product) where **semantic similarity ≈ geometric closeness**. Learned from data (word2vec, or jointly in a network). They let models generalize ("king − man + woman ≈ queen") and power search, recommendations, and NLP.

**Q16. What's the difference between fine-tuning and prompting an LLM? (bonus, very current)**
**Prompting/in-context learning** steers a frozen model via the input (zero/few-shot) — cheap, no training. **Fine-tuning** updates the model's weights on task data — stronger for specialized tasks but costlier; **parameter-efficient fine-tuning (LoRA)** updates a small adapter instead of all weights. Mention **RAG** (retrieval-augmented generation) as the go-to for grounding an LLM in your own data without retraining.

### 4.4 ML System Design — the framework
New-grad ML design is lighter but shows seniority. Use this **6-step spine** for any prompt ("Design YouTube recommendations / a news feed / spam detection / search ranking"):

1. **Clarify & scope** — the problem, the business metric (engagement? revenue?), scale (users, QPS, latency budget), online vs batch.
2. **Frame as ML** — what's the target/label? Is it classification, ranking, regression, retrieval?
3. **Data & features** — sources, labels (implicit like clicks vs explicit), features (user, item, context), and the label-leakage traps.
4. **Model** — start simple (logistic regression / gradient-boosted trees baseline) → then deep models (two-tower retrieval + a ranking model). Justify.
5. **Serving** — the classic **two-stage funnel: candidate generation (retrieval, fast, recall-oriented) → ranking (heavier, precision-oriented) → re-ranking (diversity, business rules).** Online features, caching, latency.
6. **Evaluation & iteration** — offline metrics (AUC, NDCG, recall@k) **and** online **A/B tests** on the business metric; monitoring, feedback loops, and **data/concept drift.**

**Worked mini-example — "Design a video recommendation system":** Business metric = long-term watch-time (not just clicks, to avoid clickbait). Two-stage: (a) **candidate generation** via a two-tower model (user-tower & video-tower → embedding nearest-neighbor lookup over millions of videos, fast); (b) **ranking** via a deeper model scoring ~hundreds of candidates on rich features (watch history, freshness, creator, context) to predict watch-time; (c) **re-rank** for diversity and freshness. Evaluate offline with NDCG, ship behind an **A/B test** on watch-time, watch for **feedback loops** (rich-get-richer) and **drift.**

## 5. CS Fundamentals — Rapid-Fire Q&A ⚙️

Short, correct, confident. A sampler (drill the full list):

- **Process vs Thread?** Process = independent program with its own memory; Thread = lightweight unit *within* a process sharing its memory (faster context switch, but needs synchronization).
- **Deadlock — 4 conditions?** Mutual exclusion, hold-and-wait, no preemption, circular wait. Break any one to prevent it.
- **Stack vs Heap memory?** Stack = fast, automatic, LIFO, for local variables/call frames; Heap = manual/dynamic, larger, for objects that outlive a function.
- **Process scheduling?** FCFS, Round-Robin, SJF, priority — trade-offs in latency vs throughput vs starvation.
- **SQL vs NoSQL?** SQL = structured schema, ACID, joins, vertical scale (Postgres/MySQL). NoSQL = flexible schema, horizontal scale, eventual consistency (Mongo, Cassandra, DynamoDB). Choose by data shape + scale + consistency needs.
- **ACID?** Atomicity, Consistency, Isolation, Durability — the guarantees of a reliable transaction.
- **Normalization?** Organizing tables to reduce redundancy (1NF→3NF); denormalize for read performance.
- **What is an index?** A data structure (usually B-tree/hash) that speeds reads at the cost of write speed and storage.
- **TCP vs UDP?** TCP = reliable, ordered, connection-oriented (web, email); UDP = fast, connectionless, no guarantees (video, games).
- **What happens when you type a URL and hit enter?** DNS resolve → TCP/TLS handshake → HTTP request → server processes → response → browser renders. (Be ready to go deep on any step.)
- **OOP 4 pillars?** Encapsulation, Abstraction, Inheritance, Polymorphism — with a one-line example each.
- **Big-O of common operations** — hash lookup O(1) avg, balanced BST O(log n), sorting O(n log n), etc.

### Elaborate STAR example (student version)

**Q (Ownership / Deliver Results): "Tell me about a challenging project you delivered."**
- **S:** "In my final-year capstone, our 4-person team was building an ML model to detect diseased crops from leaf images. Two weeks before the deadline our accuracy was stuck at ~72% — well below the 90% our faculty guide expected — and morale was low."
- **T:** "As the ML lead, I owned getting us to a demo-able, accurate model on time."
- **A:** "I dove deep into the errors and found two root causes: a **class imbalance** (one disease dominated the dataset) and **overfitting** (train 95% vs val 72%). I (1) applied data augmentation and class weighting to balance it, (2) added dropout and early stopping to curb overfitting, and (3) switched from training from scratch to **transfer learning** with a pre-trained ResNet, which suited our small dataset. I also set up a shared results tracker so the team stopped duplicating experiments."
- **R:** "Validation accuracy jumped to **93%**, we delivered the demo two days early, and the project was graded the top capstone in our cohort. I learned that diagnosing *why* a model fails beats blindly trying architectures."
- **Why it works:** specific root-cause (Dive Deep), personal ownership ("I"), real ML depth, and a **quantified** result.

### More behavioral questions to prepare (write a STAR for each)
Tell me about a time you: failed / had a conflict with a teammate / had to learn something quickly / received tough feedback / disagreed with a decision / took a risk / went beyond what was asked / had a tight deadline / were most proud of / had to make a decision with incomplete data. Plus: **"Why Amazon/Google?"** and **"Why should we hire you?"** (be specific, tie to the team/mission).

> *"Under pressure, you don't rise to the occasion — you sink to the level of your preparation."* Rehearse these **out loud** until they're natural, not memorized.

## 7. The Process — Timelines, Applications, Referrals 🎯

- **Apply early.** New-grad requisitions open and fill fast (often 6–9 months before start). Apply the day roles post.
- **Get referrals.** A referral dramatically increases callback odds. Ask alumni, seniors, LinkedIn connections at the company — send a short note + your resume + why you're a fit. Don't be shy; most engineers are happy to refer a prepared candidate.
- **Amazon flow (typical):** Online Assessment (2 coding problems + work-style survey + sometimes work-simulation) → 1 phone/virtual → **"The Loop"** (3–4 rounds: coding + behavioral, including a **Bar Raiser**). Expect LP behavioral in *every* round.
- **Google flow (typical):** Online coding assessment / phone screen → **on-site (4–5 rounds)**: mostly DSA, some on ML/CS fundamentals for AI teams, plus Googleyness. Then **hiring committee** review → **team match**. It can be slow; keep other options warm.
- **Also apply to:** Microsoft, Meta, Nvidia, Adobe, and strong AI startups — reps in real interviews make you better for the top choices, and they're great offers in their own right.

## 12. Interview-Day Playbook 🧭

1. **Clarify first.** Never start coding immediately. Restate the problem, ask about input size, edge cases, constraints. (Interviewers *reward* this.)
2. **Think out loud.** Narrate your approach *before* coding. Discuss brute-force → then optimize. Silence is the enemy.
3. **State complexity** (time & space) for your approach — proactively.
4. **Write clean code.** Good names, small functions. Talk as you type.
5. **Test it.** Walk through an example; check edge cases (empty, single element, duplicates, overflow).
6. **On follow-ups, stay calm.** "Great question — let me think about the trade-off." They *want* to see how you handle escalation.
7. **Behavioral: STAR, use "I", quantify, be concise** (~2 minutes/story), then stop.
8. **Ask thoughtful questions** at the end — about the team, the tech, the growth. Shows genuine interest.
9. **If you're stuck:** verbalize what you've tried, restate the goal, try a smaller example. A structured struggle still scores; frozen silence doesn't.
